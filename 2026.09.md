## heuristics

* cardinality
* naming conventions analysis e.g. `foo.id` and `bar.foo_id`
* value containment / overlap — does every value in `bar.foo_id` exist in `foo.id`? (anti-join / `EXCEPT`). This is the actual IND-discovery core and the one signal that doesn't depend on the schema author following a naming convention — naming-only detection has high false-negative rates on surrogate keys per the profiling literature
> [!NOTE]
> afaik https://schemaspy.org/ and DBeaver / DataGrip take this approach (naming-only)

# 🤖 CC

## prior art

Nobody's shipped the exact thing (CLI-first, SQLite-targeted, outputs a flat joins table + diagram), but the *problem* has real history in two separate worlds that don't talk to each other much:

**Academic / data-profiling world** — this is called **inclusion dependency (IND) discovery**, and it's the formal name for "find foreign keys nobody declared." Algorithms: SPIDER, BINDER, SINDY (BINDER is ~26x faster than SPIDER, >2500x faster than the naive MIND approach). Reference implementations live in [Metanome](https://hpi.de/en/database-group/projects/data-integration-projects/data-profiling-and-analytics/metanome-data-profiling/) (HPI) and newer [Desbordante](https://arxiv.org/html/2608.02213v1). It's proven NP-hard/W[3]-complete, which is presumably part of why "just detect joins" hasn't become a trivial solved CLI problem — the naive n²-column comparison doesn't scale, you need the divide-and-conquer tricks.

**Product world** — three tools do a version of what you're sketching:
- **[janmotl/linkifier](https://github.com/janmotl/linkifier)** — closest kin. Logistic regression over 6 features for PK guessing (position, type, `id` in name, name-similarity to table, null ratio, width) and 9 features for FK guessing (including **value range overlap with candidate PKs** — i.e. actual IND checking, not just naming). GUI-first (needs Oracle JRE + JavaFX), CLI mode exists but secondary. 51 stars, modestly maintained, MSSQL/MySQL/Oracle/Postgres — **no SQLite**.
- **[SchemaCrawler](https://www.schemacrawler.com/weak-associations.html)** — has a `--weak-associations` flag that infers undeclared FKs, but it's naming-based only, bolted onto a much bigger schema-doc tool (your own "bad DX" complaint about SchemaSpy applies here too).
- **[Azimutt](https://azimutt.app/docs/schema-exploration)** — does schema analysis that flags `_id`/`_ids` columns without a declared relation and suggests one. Closest to your "heuristics" section, but it's a web app, not a CLI, and it's a side-feature of a broader ERD/exploration product, not the whole product.

So: the gap you're circling — **a CLI, SQLite-native, that treats "what joins to what" as the entire product surface and outputs something pipeable (flat table / d2) rather than an interactive diagram** — really does look open. Everything that does inference well (Linkifier, Metanome/BINDER) is GUI or library-shaped and ignores SQLite; everything that's CLI/pipeable and touches SQLite (`datasette inspect`, `sqlite3 .schema`) doesn't infer anything undeclared, it just reads what's already there.

## critique

**"WHY NOT" isn't actually a case against building this — reread it as an argument *for* the CLI shape.** The Code Mode point ("SQL is kind of like grep, why build an index when the agent can just query") is the same argument people made against `ctags`/LSP before Claude Code shipped both `grep` *and* a deterministic index underneath it. The reframe: `wtfk` isn't a replacement for pointing an agent at the DB — it's the thing the agent shells out to, the same way it shells out to `grep` instead of re-deriving symbol locations by reading every file. A cheap, deterministic, cacheable joins-index is strictly complementary to "agent runs SQL," not competing with it. I'd cut or soften the WHY NOT section, or invert it into a "this is why CLI-not-MCP-tool-not-vector-index" argument.

**Naming-convention heuristics alone will underperform** — the profiling literature you'd be competing with is explicit that naming-based FK detection has high false-negative rates on surrogate keys and non-standard conventions. Linkifier's actual differentiator is checking **value containment** (does every value in `orders.customer_id` exist in `customers.id`?) alongside naming — that's the IND-discovery core, and it's cheap to do in SQLite (`NOT EXISTS` anti-join, or `EXCEPT`) without needing Metanome-grade algorithms at your table counts. I'd add "containment/overlap check" as a third heuristic next to cardinality and naming — it's the one signal that's actually hard to fake and doesn't depend on the schema author having followed a convention.

**One free win the PATHFINDER section is missing**: for SQLite specifically, `PRAGMA foreign_key_list(table)` gives you every *declared* FK with zero parsing — no DDL-scraping needed, unlike the Django/Rails convention-mining you sketched. That should be step 0 before any heuristic runs: declared FKs first, heuristics only for the gap. Worth a line under DDL.

**SQLite-first is a fine v1 scope call**, but flag the tension honestly: the "learn a new codebase fast" motivation you lead with is disproportionately a Postgres/MySQL problem in practice, and SQLite is being chosen for implementation convenience (single file, PRAGMA introspection) rather than because that's where the pain lives. That's a legitimate sequencing choice — prove the heuristics on the easy target, extend via the ADBC/DuckDB streaming path you already sketched in SAMPLING — just worth stating as "SQLite is the sandbox, not the endgame" rather than leaving it implicit.

# SAMPLING?

Given that we're going to have to look at the actual data, assume we'll need to sample:

> MongoDB Compass samples 1,000 documents from a collection using the `$sample` operator via the aggregation pipeline. This provides efficient, random sampling without replacement over an entire collection, or over the subset of documents specified by a query. https://www.mongodb.com/docs/compass/sampling/#std-label-compass-sampling

Or maybe pull everything into Arrow? https://arrow.apache.org/adbc/current/index.html

To analyze all keyed relationships across N tables without exhausting your memory, you can combine ADBC's native Arrow integration with a streaming execution engine like DuckDB.

Because ADBC fetches data in streaming record batches (rather than loading the entire dataset into RAM at once), you can pipe this stream straight into DuckDB to perform your key relationship analysis (such as calculating foreign key coverage, checking cardinality, or finding orphans) completely out-of-core.

Here is the most memory-efficient architecture to analyze your tables without sampling.

## Step 1: Install Required Libraries

You will need the ADBC driver for your specific database (using PostgreSQL as an example) and DuckDB.

```sh
pip install adbc-driver-postgresql duckdb pyarrow
```

## Step 2: Stream Data to DuckDB Out-Of-Core

Instead of calling .fetch_arrow_table() (which pulls everything into memory), you use .fetch_record_batch_reader(). This creates a zero-copy Arrow stream that DuckDB can query sequentially.

```python
import adbc_driver_postgresql.dbapi as dbapiimport duckdbimport pyarrow as pa

# 1. Initialize your DB URI
uri = "postgresql://username:password@localhost:5432/my_database"tables_to_analyze = ["orders", "order_details", "products", "customers"]

# 2. Start a local DuckDB instance (can spill to disk if memory limits are hit)db = duckdb.connect()
db.execute("SET max_memory='4GB'") # Restrict DuckDB RAM; it will use disk swap seamlessly

# 3. Stream each table into DuckDB as a virtual view# Note: Keep the ADBC connection open while DuckDB processes the streamswith dbapi.connect(uri) as conn:
    with conn.cursor() as cursor:
        for table in tables_to_analyze:

            # Execute the query on the remote DB
            cursor.execute(f"SELECT * FROM {table}")
            
            # Create a PyArrow stream reader (Constant memory footprint!)
            record_batch_reader = cursor.fetch_record_batch_reader()
            
            # Register this live stream directly inside DuckDB as a view
            arrow_dataset = pa.dataset.dataset(record_batch_reader)
            db.register(f"view_{table}", arrow_dataset)
        
        # 4. Perform your relationship analysis inside DuckDB
        # Example: Analyze Referential Integrity / Orphan Keys between Orders and Customers
        print("Analyzing relationship: view_orders.customer_id -> view_customers.id")
        
        analysis_query = """
            SELECT 
                COUNT(*) as total_orders,
                COUNT(DISTINCT o.customer_id) as unique_customer_keys_used,
                COUNT(CASE WHEN c.id IS NULL THEN 1 END) as orphan_order_records
            FROM view_orders o
            LEFT JOIN view_customers c ON o.customer_id = c.id
        """
        
        # DuckDB processes the Arrow stream chunk-by-chunk and returns the result
        result = db.execute(analysis_query).df()
        print(result)
```


## Why this solves your Memory Problem

* Zero-Copy Streaming: The fetch_record_batch_reader() pulls data from your database server in small chunks (usually 1024 rows at a time). As soon as DuckDB processes a chunk, Arrow discards it from memory.
* DuckDB Out-of-Core Engine: If your $N$ table joins require more memory than your system has available, DuckDB's execution engine automatically spills intermediate join tables to temporary disk storage rather than throwing an Out-Of-Memory (OOM) error.
* No Database Overhead: The heavy lifting (the join and relationship analysis) happens on your local machine using the streamed data, meaning you won't crash or slow down your production database.
