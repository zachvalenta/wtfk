🕵️‍♂️ How the Micro-Engine Infers Hidden Relationships

When a schema is messy (e.g., no explicit FOREIGN KEY constraints defined in the DDL, mismatched column names, or mixed data types), a human engineer looks for patterns. Your Python script can automate this human pattern-matching using three ultra-fast, local layers:

Layer 1: Naming & Semantic Similarity (The Metadata Scan)

Before touching the data, the tool maps the table schemas. It looks for common entity-linking patterns across different tables.
• The Logic: If Table A has a column named user_id or uid or UserNo, and Table B has a column named id or user_id, the script flags them as a potential match.
• The Micro-Tool: You don't need a heavy LLM for this. You can use standard Levenshtein distance (string similarity) or a tiny, 15MB local text-embedding model (like all-MiniLM-L6-v2) via the sentence-transformers library to catch semantic matches (e.g., mapping cust_num to client_id).

Layer 2: Value Set Intersection (The Data Profiling Scan)

This is where the engine actually proves the relationship statistically. For any two columns flagged in Layer 1, it checks if the data actually aligns.
• The Logic: If Column X is a Foreign Key pointing to Primary Key Y, then the distinct values in Column X must be a subset of the distinct values in Column Y.
• The Optimization: Querying distinct values on a 20GB database can be slow. Instead of running heavy SELECT DISTINCT queries across everything, the micro-engine samples the data or uses HyperLogLog sketches to instantly estimate set intersections. If 99% of the values in orders.uid exist in users.id, a hidden relationship is mathematically confirmed.

Layer 3: Cardinality & Entropy Analysis (The Structural Check)

The engine evaluates the nature of the data distribution to determine the direction of the relationship (which table is the parent, and which is the child).
• The Logic: A Primary Key must be unique (high entropy). A Foreign Key will have repeating values (lower entropy, many-to-one relationship). By measuring the uniqueness ratio of the overlapping data, the engine determines that users.id (100% unique) is the parent, and orders.uid (highly repeating) is the child.
